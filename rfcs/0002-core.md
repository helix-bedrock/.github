# RFC 0002: Core, regions and threads

**Status:** Accepted by the project lead (2026-10-11).
**Topics:** 1 (core: tick loop, worlds and dimensions, threading, region
ticking, core count) and 1a (where API calls run).

## Problem

Goal 8 asks for an engine that uses one core or all of them, chosen by the
server owner, with the same results either way. A survival server with many
spread-out players must use many cores inside one world, not only one core
per world. Changing the threading model later would mean rewriting the
engine and every plugin, so it is decided now.

## Decisions agreed so far

1. **Regions that merge and split as players move** (as in Folia), built in
   from the start. There is no single-threaded first version.
2. **Core limit:** one total number, `Cores`, plus optional limits per system
   (ticking, world generation, network, saving). `Cores: 1` runs everything on
   one core and is fully supported.
3. **Listeners run on the region that owns the event.** Two regions may run
   the same listener at the same time.
4. **Crossing regions is explicit:** `world.RunAt(pos, fn)` and
   `player.Run(fn)` run code on the owner's next tick.
5. **Server-wide state** (player list, scoreboards, chat, commands, game rules,
   time, weather, world border) lives on a single global owner, reached by
   safe calls.
6. **Teleports are always asynchronous,** even inside one region, and report
   when they finish.
7. **A region over its tick budget fires a warning event.**
8. **Worlds can be loaded and unloaded while the server runs** from the first
   version.

## Proposed design

### Sections and regions

- Each world is divided into **sections**: square groups of chunks, N × N
  with N a power of two.
- Loaded sections that are close together form one **region**. Regions that
  come within a merge distance of each other merge; a region whose parts no
  longer touch splits at the end of its tick.
- Rules that keep regions safe:
  - A region never grows while it is ticking.
  - It keeps a buffer of loaded chunks around its edge.
  - It never starts a tick while touching another region; touching regions
    merge first.
- Region states: ready, ticking, waiting to merge, dead.
- Section size and merge distance are settings. Their defaults are chosen by
  benchmark in `helix-bench`, not copied.

### Scheduling

- A pool of tick workers, sized by `Cores` or `TickCores`.
- Each region has its own 20 TPS schedule with a 50 ms deadline. The region
  whose next tick is due earliest runs first. A slow region does not slow the
  others.
- A region that misses its deadline fires a warning event with the region,
  the time it took and what used the time. It is not stopped.
- With `Cores: 1`, regions tick one after another in a fixed order, so a run
  can be reproduced exactly.

### Inside a region

- A region ticks its chunks, blocks, entities and players in a fixed order,
  so redstone and combat give the same result on any number of cores.
- The exact order is taken from BDS behaviour and documented in its own RFC;
  it is not guessed.
- Game time and weather are copied from the global owner at the start of
  each region tick, so they do not change during a tick.

### The global owner

- One goroutine that ticks at 20 TPS and never splits.
- Owns the player list, scoreboards, chat, commands, game rules, time,
  weather and the world border. Folia left scoreboards unsolved; owning them
  here solves that.
- Regions and plugins reach it through safe calls that run on its next tick.

### Worlds

- Worlds and dimensions are loaded and unloaded at runtime. Unloading waits
  for pending teleports, saves every region, then removes the world.

### Crossing regions

- `world.RunAt(pos, fn)` queues `fn` for the next tick of the region that owns
  `pos`, loading it if needed.
- `player.Run(fn)` and `entity.Run(fn)` queue `fn` on whichever region owns
  the player or entity when the queue runs, following it as it moves.
- Teleports: the entity leaves its region, then is placed in the target region
  on that region's next tick. The call returns a result that completes when
  the entity has arrived, or fails with a reason.

### Safety

- Every object owned by a region knows its owner.
- In debug mode, calling a region-owned object from the wrong place fails
  loudly at the bad call, naming the caller and the owner.
- In normal mode the call is logged and refused. The server never panics.

### Worker pools

- Chunk generation, lighting, saving, compression and packet encoding run on
  their own pools, limited by the per-system settings, and never touch live
  region data directly.

## Prior art

| Project | Model | What we take | What we avoid |
|---|---|---|---|
| Folia ([PaperMC docs](https://docs.papermc.io/folia/reference/overview)) | Regions of sections that merge and split; per-region 20 TPS on a pool, earliest deadline first; a global region; per-location, per-entity and global task queues; async-only teleports | The region model, scheduling, task queues, async teleports | Scoreboards and world loading left unsolved; most plugins break because the API was retrofitted |
| Minestom (`ThreadDispatcher`, `Acquirable`) | Partitions (such as chunks) assigned to a fixed number of tick threads by a pluggable `ThreadProvider`; `Acquirable` locks an entity to the current thread or runs code synchronised with it | Pluggable assignment, and checking whether an object is local to the current thread | Locking another thread's entity from anywhere: easy to deadlock, and it hides cross-thread access |
| Dragonfly (`world.Tx`) | One goroutine per world; all world access goes through a transaction handle valid only during its callback | Access only through a handle valid during the call: the closest Go model to owner scheduling | Only one core per world |
| Pumpkin | Worlds, players and entities ticked with `par_iter` | Worker pools for side work | Order is not fixed, so results differ between runs and core counts |
| MultiPaper | One world across several server processes; a master assigns chunk ownership and syncs changes between servers | Each chunk has one owner at a time | Several processes, and plugins that must keep no local state; out of scope for one server |

## Open questions

- Default section size and merge distance (decided by benchmark).
- The fixed tick order inside a region (from BDS).
- How entities that move faster than a section per tick (projectiles,
  minecarts) cross region edges.
- How a region requests chunk loads, and how long it waits for them.

## Alternatives considered

- **One goroutine per world** (Dragonfly): simple and safe, but one busy
  world uses one core, and moving to regions later would rewrite the engine
  and every plugin. Rejected.
- **A fixed grid of regions:** many cores, but the grid does not follow
  players and every crossing needs a message. Rejected for regions that
  follow players.
